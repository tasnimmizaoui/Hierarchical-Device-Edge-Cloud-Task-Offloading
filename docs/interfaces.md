# Shared interfaces — Interface v1 proposal

This is the contract between Student 1 (simulation) and Student 2 (RL). Both approve it before either side builds against it. A change to field names, units, action meanings or method signatures requires a reviewed pull request from both students.

## Canonical units

| Quantity | Unit | Convention |
|---|---|---|
| Simulation time | seconds | Floating-point simulation time |
| Input/output size | decimal MB | 1 MB = 1,000,000 bytes |
| Compute demand | MI | Million instructions |
| CPU capacity | MIPS | Million instructions per second |
| Bandwidth | Mbps | Megabits per second |
| Energy | joules (J) | Device energy tracked separately |
| Latency/deadline | seconds | Relative deadline measured from arrival |
| Utilization | fraction [0,1] | Never percentage in internal APIs |

## Shared task contract

`Task` in `mec_offloading.domain.models`:

- `task_id: str`
- `device_id: str`
- `arrival_time_s: float`
- `input_size_mb: float`
- `required_mi: float`
- `result_size_mb: float`
- `deadline_s: float` — relative deadline duration
- `priority: int = 0`

The trace adapter may provide only some fields. Every synthetic field (deadline, payload size, battery, device assignment, link conditions) must be generated by an explicit mapping/configuration and never presented as directly measured trace data.

## Shared formulas

- Serialization delay: `data_size_mb * 8 / bandwidth_mbps` seconds.
- Link transfer: serialization delay + propagation delay + modeled queue/contention delay.
- Execution time: `required_mi / capacity_mips` seconds.
- Absolute deadline: `arrival_time_s + deadline_s`.
- End-to-end latency: `completion_time_s - arrival_time_s`.
- Deadline met: `completion_time_s <= arrival_time_s + deadline_s`.
- First-order radio energy: transmit power (W) × transmit time (s) = J.
- First-order CPU energy: calibrated energy-per-MI coefficient × MI = J.

The formulas are primitive model components, not a complete energy model. State clearly whether idle, receiving, retransmission and network infrastructure energy are included.

## Decision interfaces

- Device: `choose(task, device_state, edge_state) -> DeviceAction`
  - `EXECUTE_LOCAL = 0`
  - `OFFLOAD_TO_EDGE = 1`
- Edge: `choose(task, edge_state, cloud_state) -> EdgeAction`
  - `EXECUTE_AT_EDGE = 0`
  - `FORWARD_TO_CLOUD = 1`
- Cloud: `choose_rule(queue_summary, cloud_state) -> CloudSchedulingRule`
  - `EDF = 0`, `SHORTEST_PROCESSING_TIME = 1`, `FIFO = 2`

The cloud RL agent initially selects one scheduling rule per dispatch decision. It is an RL-controlled scheduler, not an agent selecting arbitrary task IDs. Keep baseline EDF as a distinct fixed policy. Any change to direct task-index selection requires a jointly revised action/observation contract.

## Minimum observations — v1 proposal

Device: normalized task demand, input size, remaining deadline, battery fraction, local CPU capacity, device-edge bandwidth.

Edge: normalized remaining deadline, task demand, input size, edge CPU utilization, edge queue wait, edge-cloud bandwidth, cloud congestion.

Cloud: cloud CPU utilization, queue length, minimum and mean remaining deadline, mean estimated execution time, oldest queue wait.

All normalization scales must be configuration values used identically in training and evaluation. Clip to a documented range. Use fixed-shape arrays for DQN v1.

## Policy and backend interfaces

`mec_offloading.domain.ports` defines framework-independent `Protocol` interfaces:

- `DevicePolicy.choose(...)`
- `EdgePolicy.choose(...)`
- `CloudSchedulingPolicy.choose_rule(...)`
- `SimulationBackend.run_episode(...)`

The simulator/domain layers must not import Gymnasium or Stable-Baselines3. RL adapters implement these protocols at the boundary.

## Result contract

For each completed or failed task, report task ID, route, arrival/completion time, end-to-end latency, deadline status, device energy, communication delay, communication bytes, and nullable failure reason. Per-level decision logs should include timestamp, task ID, agent name, local observation, action, reward and relevant context. Aggregate results and detailed event logs should be separate.
